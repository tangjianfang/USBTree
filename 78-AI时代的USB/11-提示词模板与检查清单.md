# AI × USB 提示词模板与检查清单

> 🌿 知识树位置: 树干 → 枝干[AI 时代的 USB] → A 篇 · 叶
> ⬆️ 返回: [00-索引](00-索引.md)

以下模板均为**【经验】**总结，可直接复制使用。`{花括号}` 是要替换的部分。它们共同的骨架是：**限定资料来源 → 要求引用 → 允许"不知道" → 规定输出格式**。

## T1 规范问答（配合 RAG）

```text
你是 USB/BLE 协议助手。只依据下面【资料】回答，不得使用资料以外的记忆补全数字。
规则：
1. 每个数字、字段值、编码、时序参数后标注 [资料编号]，并写出资料中给出的规范名、修订号、章节/表号。
2. 资料未覆盖的写「资料未覆盖，需查规范原文」。
3. 同一字段在不同规范版本（如 USB 2.0 与 USB 3.x）含义不同时，分别列出。
4. 资料冲突时按 官方规范原文 > Key Facts > 讲解正文 取舍，并指出冲突。
输出：①结论（≤5 行）②依据（逐条带出处）③未覆盖/待核实项。
【资料】{检索结果}
【问题】{问题}
```

## T2 独立核对（新会话执行）

```text
下面是另一位助手的回答和它引用的原文。逐条核对回答中的每个数字和断言：
- 原文中能找到逐字依据 → 标「✔ 有据」并引用原文句子；
- 原文中找不到 → 标「✘ 无据」；
- 原文与回答矛盾 → 标「✘ 矛盾」并给出原文。
不要补充新知识，不要改写结论，只做核对。
【回答】{T1 的输出}
【原文】{T1 用到的资料}
```

## T3 生成 HID 报告描述符

```text
为下面的设备生成 HID 报告描述符（HID 1.11，Usage 以 HUT {版本号} 为准）：
- 设备：{例：5 键鼠标 + 16 位 X/Y + 滚轮 + 水平滚轮}
- Report ID 规划：{例：ID 1 = 鼠标输入，ID 2 = 厂商 Feature 64 字节}
- 是否需要引导协议兼容：{是/否}
要求：
1. 输出 C 数组，每个条目一行，行尾注释写条目名与含义；每个 Usage 注释写 HUT 章节。
2. 列出每个报告的位数合计，必须是 8 的整数倍。
3. Logical Minimum/Maximum 注意有符号编码（例如 255 要写成 26 FF 00）。
4. 最后单独列出「我不确定的 Usage」清单。
```

交付前用 [02 篇](02-AI生成与审查描述符.md) 的 `hid_lint.py` 和 `hidrd-convert` 回读校验。

## T4 抓包分析

```text
背景：{设备类型、VID:PID、速度（FS/HS/SS）、主机系统、症状与复现步骤}
材料来源：{usbmon / USBPcap / 硬件分析仪型号}。
注意：软件抓包看不到 SOF、NAK 重试、chirp、LPM 等总线层事件，不得就这些事件下结论。
期望行为：{例：GET_DESCRIPTOR(Device,8)→SET_ADDRESS→GET_DESCRIPTOR(Device,18)→GET_DESCRIPTOR(Config)→SET_CONFIGURATION}
设备描述符（lsusb -v）：{粘贴}
抓包 CSV（帧号,时间,源,目的,类型,S/C,状态,长度,bRequest）：{粘贴}
请输出：
1. 时间线摘要（≤10 行，引用帧号）；
2. 最多 3 个假设，每个附：支持证据帧号、反对证据、置信度（高/中/低）；
3. 下一步：为区分这些假设，需要什么额外抓包或实验。
```

## T5 驱动代码审查（Windows KMDF 示例）

```text
审查下面的 KMDF USB 驱动代码。只报告问题，不重写代码。逐项检查：
1. 每个 WDFREQUEST 是否在所有路径上恰好完成一次；取消与完成是否竞争；
2. 各回调的 IRQL 约束是否满足（DISPATCH_LEVEL 下无分页代码、无等待）；
3. 连续读失败、管道 STALL 后的复位/恢复路径；
4. 选择性挂起/电源策略与 I/O 到达时的唤醒；
5. 意外移除后是否仍有 I/O 引用硬件；
6. 缓冲区长度是否以设备返回的实际长度为准。
每个问题给：文件:行号、严重度（崩溃/数据错误/资源泄漏/风格）、依据（WDF 文档名或规则名）。
{代码}
```

## T6 设备固件骨架（TinyUSB 示例）

```text
用 TinyUSB 为 {MCU 型号} 生成复合设备骨架：{例：CDC-ACM + HID（自定义 64 字节报告）}。
要求：
1. tusb_config.h 中 CFG_TUD_* 与描述符中接口数量一致；接口号与 IAD 的 bFirstInterface/bInterfaceCount 对得上；
2. 配置描述符 wTotalLength 用宏计算，不要手写数字；
3. 列出所有在中断上下文与任务上下文中被调用的回调，标出不能阻塞的地方；
4. VID/PID 用占位符 0xCAFE/0x4000，并提醒量产必须换成自有 VID。
```

## T7 模糊测试规格起草

```text
依据下面的 {设备类} 规范原文片段，起草 syzkaller 的 USB 设备描述（或 Facedancer 设备模型），
覆盖：描述符各字段的合法范围与边界值、类特定请求的结构与长度。
对规范中「保留」「厂商定义」的字段，生成越界值用例。
输出后我会用 syz-extract / syz-generate 校验，并把报错原样反馈给你修正。
【规范片段】{粘贴，带章节号}
```

## T8 带宽/功率预算

```text
帮我做 USB 预算，只能用下面给出的规范参数，所有数字写出算式：
- 总线：{USB 2.0 HS / USB 3.2 Gen 1 / …}；规范参数：{例：HS 同步单端点 3×1024 B/微帧；周期性传输 ≤80% 微帧}
- 负载：{例：2 路 1280×720 NV12 30 fps + 8 通道 16 kHz 16 bit 麦克风}
- 供电：{端口类型与 PD 档位}；负载功率：{厂商标称值并注明口径}
输出：每路需求、合计、余量百分比、超限项与可选方案（降分辨率/换压缩格式/分控制器/有源集线器）。
```

## 交付前检查清单

在把任何 AI 产出（答案、描述符、代码、分析报告）用到项目里之前：

- [ ] 每个协议数字都有规范名 + 修订号 + 章节/表号，并且至少抽查一个回到原文核对
- [ ] 涉及跨版本字段（`bMaxPacketSize0`、`bInterval`、编码方式、速率命名）时已分别确认
- [ ] 描述符经过独立解析器回读（`hidrd-convert` / `hid-decode` / `lsusb -v`），结果与需求逐项一致
- [ ] 抓包分析的结论都引用了帧号，且没有对软件抓包不可见的事件下结论
- [ ] 驱动/固件代码经过编译器零告警、静态分析（如 CodeQL）与真机拔插/睡眠唤醒测试
- [ ] Agent 可调用的工具已按可逆性分级，L2/L3 操作需要人工确认（见 [05 篇](05-Agent硬件在环测试与安全护栏.md)）
- [ ] 产品/器件建议已核对当前供货与维护状态
- [ ] 文中【经验】【观点】与【事实】已分开标注
