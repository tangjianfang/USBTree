# 机器人与具身智能中的 USB

> 🌿 知识树位置: 树干 → 枝干[AI 时代的 USB] → B 篇 · 叶
> ⬆️ 返回: [00-索引](00-索引.md) · 前置: [四种传输类型](../10-树干-USB核心/06-四种传输类型.md) · [物理层与电气特性](../10-树干-USB核心/03-物理层与电气特性.md)

具身智能机器人的"大脑"常是一台带 GPU/NPU 的计算机，身上的相机、深度传感器、IMU、麦克风、CAN 总线转换器大量通过 USB 接入——因为 USB 便宜、即插即用、驱动现成。但 USB 是为桌面外设设计的，放到电机旁边、放进控制回路里，就要清楚它的边界。

## 一、USB 的时间特性：轮询、量化与抖动

**【事实】** USB 是主机调度的轮询总线，设备不能主动发起传输。中断端点的轮询周期由 `bInterval` 决定：全速单位 1 ms（1~255），高速为 2^(bInterval−1) × 125 µs（见[四种传输类型](../10-树干-USB核心/06-四种传输类型.md)）。总线时间以帧（全速 1 ms）和微帧（高速 125 µs）为调度单位。

**【观点】** 由此得出三个工程结论：

1. **全速设备的数据在主机侧以 1 ms 为量化粒度到达**，高速设备是 125 µs。用全速 CAN-USB 转换器做 1 kHz 以上的控制回路，相位误差就以毫秒计。
2. **USB 层的周期是确定的，但端到端不是**。主机控制器把完成事件交给操作系统后，何时被线程处理取决于中断合并、调度器、CPU 负载；通用 Linux/Windows 不保证这段时间的上限。
3. **共享控制器的设备互相影响**。多台摄像头与 CAN 转换器挂在同一个控制器下时，带宽预留与中断负载会叠加（摄像头带宽不够时的 `-ENOSPC` 见 [07 篇](07-UVC与UAC喂给模型-带宽与延迟计算.md)）。

## 二、与 EtherCAT、CAN、以太网对比

**【事实】** EtherCAT 的分布时钟（Distributed Clocks）可使各从站同步抖动显著小于 1 µs（[EtherCAT Technology Group · 技术介绍](https://www.ethercat.org/en/technology.html)）。CAN 在 Linux 上通过 SocketCAN 子系统以网络接口形式提供（[内核文档 · SocketCAN](https://docs.kernel.org/networking/can.html)）。

| 维度 | USB（2.0/3.x） | EtherCAT | CAN / CAN FD | 标准以太网（UDP/GigE 相机） |
|---|---|---|---|---|
| 拓扑 | 主机为中心的树形，经集线器扩展 | 线形/环形，帧"飞读飞写"穿过各从站 | 多主广播总线 | 交换式星形 |
| 同步/确定性 | 帧/微帧周期确定；端到端依赖主机 OS | 分布时钟抖动 ≪ 1 µs（官方口径） | 仲裁确定；带宽小 | 尽力而为（需 TSN 等增强） |
| 线缆长度 | USB 2.0 规范建议 5 m（见[物理层](../10-树干-USB核心/03-物理层与电气特性.md)） | 节点间可达百米级（以太网物理层） | 随位速率下降 | 百米级 |
| 供电 | VBUS / PD | 一般外部供电 | 外部供电 | 可用 PoE |
| 适合 | 相机、深度传感器、调试口、低频传感器 | 关节伺服、硬实时运动控制 | 电机驱动器、电池管理、底盘 | 多相机、远距离、大带宽 |

**【观点】** 一个常见且合理的分层：**伺服控制回路走 EtherCAT 或 CAN，感知数据走 USB 3.x 或以太网，USB 2.0 留给调试与低频传感器**。把关节力矩控制放进 USB 回路里，是具身智能原型机里最常见的"能跑但跑不稳"的根源。

## 三、CAN-USB 转换器

**【事实】** Linux 主线内核里有两类常见的 CAN-USB 驱动（见 `drivers/net/can/usb/Kconfig`）：

| 驱动 | 支持的设备 | 说明 |
|---|---|---|
| `gs_usb` | Geschwister Schneider 与 candleLight 兼容设备（开源固件 [candleLight_fw](https://github.com/candle-usb/candleLight_fw)） | 开源硬件/固件生态，适合做二次开发 |
| `peak_usb` | PEAK-System PCAN-USB 系列，覆盖 CAN 2.0b 与 CAN FD | 商用产品线 |

两者都把转换器暴露为 SocketCAN 网络接口（如 `can0`），上层用 `ip link` 配置位速率、用 `candump`/`cansend` 或程序读写。

```bash
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 up
candump can0
```

**【计算】** 经典 CAN 在 1 Mbit/s 下，一帧标准格式、8 字节数据的帧不计位填充约 108 位（帧格式开销 44 位 + 数据 64 位），加 3 位帧间隔约 111 位，即约 111 µs/帧，最多约 9,000 帧/秒。与之对比，全速 USB 的 1 ms 帧周期里可能堆积约 9 帧——这就是全速转换器"批量到达"的来源。

**【经验】** 选 CAN-USB 转换器时优先选高速（480 Mbit/s）型号并确认它能给每一帧打硬件时间戳；用时间戳而不是主机接收时刻做控制与日志对齐。

## 四、机器人上的 USB 工程问题

**【事实】** USB-IF 发布有《USB Type-C Locking Connector Specification》，定义带锁紧结构的 Type-C 插头机械要求与插座安装指引（[USB-IF 文档库](https://www.usb.org/document-library/usb-type-cr-locking-connector-specification)），面向需要防松脱的场景。

**【经验】**

1. **设备命名要稳定**：多台同型号相机/转换器，用 udev 规则按序列号或物理端口路径（`/dev/v4l/by-path/`、`/dev/serial/by-id/`）绑定名字，不要依赖 `/dev/video0`、`ttyACM0` 的枚举顺序。
2. **电机噪声导致掉线**：电机驱动与 USB 共地不良时，常见现象是设备反复断开重连。处理顺序：线缆屏蔽与接地 → 加隔离（USB 隔离器）→ 缩短线缆 → 换工业级集线器。
3. **振动导致接触不良**：桌面级 Type-C 插头在长期振动下容易松动；采用锁紧连接器或机械固定。
4. **供电冗余**：VBUS 从主板取电的传感器在电机启动的瞬间压降下可能复位。给关键传感器单独供电，或用有源集线器。
5. **断线自动恢复**：软件必须能处理"设备消失又出现"——监听 udev 事件重新打开设备，而不是靠重启整个节点。

## 五、AI 时代的新需求

**【观点】** 具身智能让机器人上的 USB 负载发生了两点变化：

- **多相机 + 深度 + 音频同时进模型**，单个 USB 3.x 控制器的带宽很快被占满。要按 [07 篇](07-UVC与UAC喂给模型-带宽与延迟计算.md) 的算式先算，再决定是分摊到多个控制器，还是改走以太网相机。
- **数据采集用于训练**：遥操作采集时需要多路传感器的时间对齐。USB 设备的时间戳精度参差不齐，优先选能提供硬件时间戳或支持外部触发的相机与转换器；UVC 负载头里的 PTS/SCR 字段（UVC 1.5 §2.4.3.3）可用于把帧时间映射到设备时钟。
